These conventions apply to **every** endpoint unless a page states otherwise.

## Response envelope

Every response wraps its payload in a common envelope so callers can branch on success uniformly.

| Field | Type | Meaning |
| --- | --- | --- |
| `status` | int | `1` = success, other values = failure |
| `responseMessage` | string | Human-readable status (optional on success) |
| `errorCode` | int | `0` = success, non-zero = a specific error |

<ResponseExample>
```json Envelope
{
  "status": 1,
  "responseMessage": "Success",
  "errorCode": 0
}
```
</ResponseExample>

## Coded fields — object shape

Any classification field (property type, ownership method, district…) is returned as an **object** — never a bare string. Each such object carries the same properties:

| Property | Type | Meaning |
| --- | --- | --- |
| `constant` | string | Stable machine key — **match on this** |
| `lookupNameEn` | string | English label (display) |
| `lookupNameAr` | string | Arabic label (display) |
| `lookupId` | int | Numeric id |
| `number` | string | Optional code, when present |

```json
{ "lookupId": 1039, "constant": "TOWNHOUSE", "lookupNameEn": "Townhouse", "lookupNameAr": "تاون هاوس" }
```

In the endpoint tables these fields are typed `object` (a single coded value) or `object[]` (a list of them). Match on `constant`, never on the display label. Resolve the full set of possible values via [Reference Data](/endpoints/reference-data).

## Identifiers — plot, property, owner

A **plot is not a property.** One plot can carry many separately registrable properties (units, villas, floors), and each of those can have many owners. Three identifiers follow from that, and the distinction matters because tokenization happens at the *property* level, not the plot level.

| Identifier | Identifies | Cardinality |
| --- | --- | --- |
| `plotID` | The land parcel as registered by ADREC | 1 plot → **many** properties |
| `propertyId` | A distinct registrable property within a plot — a unit, villa, or the whole plot where it is undivided | 1 property → **many** owners |
| `ownerId` | One party's ownership stake on one property | — |

<Warning>
  **`plotID` alone does not identify a tokenizable asset.** A `plotID` selects a *scope* — potentially several properties with different owners, deeds, valuations and tenancy. Anything that attaches to a single title — a signed title snapshot, a valuation, a transfer, a beneficial-owner register — must be addressed by `propertyId`.
</Warning>

### The `(plotID, propertyId)` pair

Whether `propertyId` is unique **across** the registry or only **within** its plot is [an open item with ADREC](/introduction/scope-and-reconciliation#gaps-items-to-confirm-with-adrec). Until that is confirmed, the contract is safe under either answer:

- **Callers send the pair.** Property-scoped calls carry `plotID` (path) *and* `propertyId` (query or body). Never `propertyId` on its own.
- **Responses echo the pair.** Every property-scoped response returns both `plotID` and `propertyId`, so a caller can always re-address the record it just read.

Omitting `propertyId` where the endpoint allows it widens the call to **plot scope** — the response then covers every property on the plot. Where a plot-wide answer would be meaningless, `propertyId` is marked **REQUIRED** on that endpoint.

<Info>
  If ADREC confirms `propertyId` is globally unique, a `/{propertyId}` shorthand path can be added later without breaking the pair form documented here.
</Info>

### Resolving a plot's properties

[Property Details](/endpoints/property-details) is the resolver. `GET /property/details?plotID={plotID}` returns `propertyDetails[]` — one item per property on the plot, each with its `propertyId` and its own `ownerships[]`. Add `&ownerId=` to return only the properties a given party owns.

Where the only identifier you hold is the land-department (DLD) number, [Property Details by DLD Number](/endpoints/property-details-by-dld) resolves in the opposite direction — DLD number → the `(plotID, propertyId)` pair — and returns the same record.

```
plotID 506999
├── propertyId 506999001  ownerships[] → Issuer Holding LLC (100%)
├── propertyId 506999002  ownerships[] → A (60%), B (40%)
└── propertyId 506999003  ownerships[] → Al Reem Developments LLC (100%)
```

## Units, coordinates & dates

| Topic | Requirement |
| --- | --- |
| **Areas** | Square metres. VentureOne converts to sqft for display. |
| **Coordinates** | JSON numbers (`xCoordinate`, `yCoordinate`) in the registry's projection. |
| **Currency** | ISO 4217 codes; amounts as JSON numbers. Registry money is `AED`. |
| **Dates** | ISO-8601 with timezone — `2026-06-10T00:00:00Z`. No bare dates. |
| **Booleans** | Real JSON `true`/`false`, not `1`/`0` or `"Y"`. |
| **Identifiers** | Stable across calls. See [Identifiers](#identifiers-plot-property-owner) below for the plot / property / owner hierarchy. |

## Pagination

List endpoints accept `pageNumber` (1-based) and `pageSize`, and return `totalCount`.

<ParamField query="pageNumber" type="integer" default="1">
  1-based page index.
</ParamField>
<ParamField query="pageSize" type="integer" default="20">
  Items per page. ADREC to confirm the maximum.
</ParamField>

```json Paginated response (shape)
{
  "items": [ /* … */ ],
  "pageNumber": 1,
  "pageSize": 20,
  "totalCount": 143,
  "status": 1,
  "errorCode": 0
}
```

## Idempotency (writes)

**Every write (state-changing) operation must carry an `Idempotency-Key` request header.** The key is a unique value **generated by the upstream VentureOne application** — one key per logical operation. If the same key is replayed (a retry after a timeout or network failure), ADREC returns the **original result** instead of performing the action a second time.

```http
Idempotency-Key: vo-txn-9f2c1a7e-4b10-4d3a-9e21-7c1b8a5d2f00
```

<Note>
  Applies to every write endpoint:
  [Registry Transactions](/endpoints/registry-transactions) (title transfer, annotation, charge, release) ·
  [Fee Payment](/endpoints/fee-payment) ·
  [Beneficial Owners](/endpoints/beneficial-owners) (add / update / remove / batch) ·
  [Tenancy](/endpoints/tenancy) register (if enabled).

  Read-only calls made over `POST` (e.g. [Party Verification](/endpoints/party-verification), [Owner Properties](/endpoints/owner-properties), [Fee Quote](/endpoints/fee-quote)) do **not** change ADREC state, so the key is not required for them.
</Note>

**Rules**
- Use an opaque, unique value per operation — a UUID is recommended (e.g. `vo-txn-<uuid>`).
- Keep the same key across retries of the *same* operation; use a new key for a genuinely new operation.
- Where a saga spans a quote → commit → payment, pair the key with the returned `transactionRef` so the flow can safely resume.
- ADREC should honour a replayed key for a reasonable retention window (window to be confirmed by ADREC).

## Errors

On failure, `status ≠ 1` and `errorCode` names the reason. ADREC to supply the full `errorCode → meaning` table via [Reference Data](/endpoints/reference-data). HTTP status codes should still reflect the class of error (`4xx` client, `5xx` server) even when the envelope carries the detail.
